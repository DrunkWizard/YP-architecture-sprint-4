# Потенциально проблемные места: 

- CRM API и SHOP API используют одну базу данных 
- Алгоритм, который высчитывает стоимость изделия работает слишком долго
- Мало экспертизы по C# и React
- Ручное тестирование 
- Один инстанс на БД и на приложение
- MES перегружен ответсвенностью
- Отсутсвуют метрики по которым можно было бы понять, что заказ долго висит в статусе
- Отсутсвуют метрики по которым можно было бы понять нагрузку на сервис и БД
- Нет логов и трейсинг
- Отсутсвие кэширования

# Инициативы по устранению проблем в порядке приоритета:

1. Добавить метрики и алерты для заказов + метрики на загрузку сервисов и БД
2. Разделить MES на два сервисва. Один для высчитвания стоимости изделения по 3d модельке, второй для управления прцоессами производства. Во время распила добавить кэширование заказов
3. Ограничить загружаемые модели по количеству полигонов, если это возможно 
3. Автоматизировать тестирование (E2E автотесты, юниты и интеграционные, внедрить % покрытия)
4. Добавить логирование и трейсинг
5. Выделить отдельную БД для CRM 
6. Сделать репликацию всех БД 

# Целевая архитектура через полгода: 
- Сервис MES разделен на два
- У каждого микросервисва своя БД
- Все БД и сервисвы развернуты минимум в двух репликах 
- Внедрены технологии по сбору и отоброжению метрик 
- Реализовано кэширование


---
Если бы была возможность реализовать только три инициативы за полгода, то это были бы:
- Внедрение метрик и алертов на заказы
- Автоматизация тестирования 
- Распил MES с внедрением кэширования

# Мысли: 
Первостепенно важно отлавливать проблему с заказами раньше пользователей, чтобы иметь возможность устранить их до проблем с пользовательским опытом. Поэтому первым делом нужно внедрить метрики и алерты по статусам заказов, чтобы в ручную просматривать и решать их. <br>
Без автоматизированного тестирования изменения будут попадать в продакшн дольше. Также вероятность пропустить потенциально проблемный код выше. Поэтому автоматизация тестирования является задачей с достаточно высоким приоритетом. <br>
Сервис MES выглядит перегруженным, нужно разделить его и внедрить кэшировать, чтобы снизить нагрузку и улучшить пользовательский опыт. <br>
Общее повышение observability (логи, метрики, трассировка). Чтобы лучше понимать проблемные места и устранять ошибки на упреждение до того как их увидет пользователей. <br>
Два сервиса с общей базой данных могут приводить к проблемам консистентности данных и дедлокам. Также схема данных может стать большой и непонятной. Плюс изменения в схеме могут повлиять на два сервиса, что тоже может привести к проблемам.
