# В какие части системы имеет смысл добавить кеширование 
- В систему MES нужно добавить кэш на запрос по заказам, чтобы ускорить время отдачи самых последних заказов
- Кэшировать стоимость для моделей с одинаковыми параметрами (хеш файла 3D-модели как ключ).  
- Статические элементы (например шаблоны украшений) кэшировать на стороне клиента + CDN 

# Мотивация
На данный момент системе присутсвуют следующие проблемы: 
- Высокое время расчета стоимости заказа в MES (до 30 минут для сложных моделей).
- Медленная загрузка дашборда операторов (фильтрация заказов по статусам).
- Рост нагрузки на БД из-за увеличения запросов через API партнеров.

Кэширование поможет:
- Сократить время отклика для критичных операций.
- Снизить нагрузку на БД и MES.
- Улучшить стабильность при пиковых нагрузках.

# Предлагаемое решение
**Серверное кэширование**
- Централизованное управление.  
- Согласованность данных между компонентами.  
- Возможность инвалидации по событиям (например, обновление статуса заказа).  

**Паттерн: Cache-Aside (Lazy Loading)**
- **Как работает**:  
  1. При запросе данных сначала проверяется кэш.  
  2. Если данных нет — они загружаются из БД и сохраняются в кэш.  
- **Почему Cache-Aside?**  
  - Подходит для сценариев с редкими обновлениями (например, расчет стоимости).  
  - Минимизирует нагрузку на БД при частых чтениях. 
  - Достаточно прост в реализации
- **Почему не другие паттерны**:  
  - **Write-Through**: Избыточен, так как обновления данных не настолько часты.  
  - **Refresh-Ahead**: Сложно предсказать, какие данные понадобятся заранее.

# Инвалидация
### **Гибридный подход**:
- **Временная инвалидация (TTL)**:  
  - Для данных, которые могут устаревать (каталог товаров, статические элементы): TTL=1 час.  
- **Явная инвалидация по событиям**:  
  - При изменении статуса заказа удалять ключ из кэша.  
  - При обновлении 3D-модели инвалидировать кэш расчета стоимости по хешу файла.  

### **Почему не другие стратегии**:
- **Только TTL**: Не гарантирует актуальность данных при редких обновлениях (например, статусы заказов).  
- **Только программная инвалидация**: Усложняет логику приложения, если событий много.
