# Мотивация

Мониторинг позволит узнавать о проблемах до того как они дойдут до пользователя и превентивно устранять их. Также проще будет находить узкие места сиситемы и заниматься их оптимизацией и лучше понимать каким сервисам требуется больше ресурсов. Также данные для мониторинга можно использовать в бизнес аналитике.

# Выбор подхода к мониторингу

- Для MES подойдет метод USE и RED. Для части с вычислением цены модели подойдет USE. Нужно отслеживать очередь на вычесление и очередь необработанных заказов в Rabbit как насыщенность из USE. Для отслеживания апи хорошо подойдет RED с RPS 

- Для остальной системы подойдет RED благодаря его простоте и удобству по отслеживанию проблем сервисов, которые управляются запросами

# Какие метрики использовать

### Общие метрики для API (Shop, CRM, MES):

- Number of requests (RPS)  
**Зачем**: Оценка нагрузки на каждый сервис.  
**Ярлыки**: endpoint (например, /calculate-price, /create-order), http_method (GET, POST).  
**Важность**: Поможет выявить перегрузку API после открытия доступа внешним продавцам. 

- Response time (latency)  
**Зачем**: Измерение времени ответа API.  
**Ярлыки**: endpoint, http_status.  
- Number of HTTP 200 / 500  
**Зачем**: Отслеживание успешных и ошибочных запросов.  
**Ярлыки**: endpoint, error_code (для 500).  

- Kb transferred (received/sent)
**Зачем**: Мониторинг объема данных (актуально для загрузки 3D-моделей).
**Ярлыки**: endpoint (например, /upload-model).

### Инфраструктурные метрики

- Number of dead-letter-exchange letters in RabbitMQ  
**Зачем**: Для отслеживания сообщений, которые не были обработаны из-за ошибок (например, неверный формат, недоступность потребителя).  
**Ярлыки**: queue_name (название очереди), error_type (причина попадания в dead-letter).
**Важность**: Поможет выявить сбои в интеграции CRM и MES, которые приводят к потере заказов.  

- Number of message in flight in RabbitMQ  
**Зачем**: Для мониторинга текущей нагрузки на очереди (сообщения в процессе обработки).  
**Ярлыки**: queue_name, consumer (например, MES или CRM).  

- CPU % / Memory Utilisation 
**Зачем**: Выявление узких мест в ресурсах.  
**Ярлыки**: service (например, mes-price-calculation).  
**Важность**: Медленная загрузка MES может быть связана с нехваткой CPU/памяти.  

- Size of S3 storage / Size of DB instance  
**Зачем**: Планирование масштабирования хранилищ.  
**Ярлыки**: bucket_name (для S3), database_table (например, orders).  

- Number of connections for DB instance  
**Зачем**: Предотвращение перегрузки БД.  

### Бизнес метрики
- Количество заказов  
**Зачем**: Предотвращение перегрузки БД.  
**Ярлыки**: bucket_name (для S3), database_table (например, orders).  
- Время нахождения заказа в определенном статусе


# План действий 

### 1. Развертывание инфраструктуры мониторинга
- **Развернуть Prometheus Server**  
  Создать выделенный инстанс Prometheus в Yandex Cloud с конфигурацией для сбора метрик от всех компонентов системы.  
- **Настроить экспортеры метрик**  
  Установить на все узлы:  
  - **Node Exporter** для сбора системных метрик (CPU, memory, disk).  
  - **Yandex Cloud Monitoring Exporter** для метрик Managed Databases.  
- **Развернуть Grafana**  
  Интегрировать Grafana с Prometheus и настроить источники данных.  

---

### 2. Инструментация приложений
- **Внедрить Prometheus-клиенты в API**  
  - **Java-приложения (магазин, CRM)**: Использовать **Micrometer** с Prometheus Registry.  
  - **C#-приложение (MES)**: Настроить **prometheus-net** для сбора метрик.  
  Собирать:  
  - `http_requests_total` (RPS) с ярлыками `endpoint`, `method`, `status`.  
  - `http_request_duration_seconds` (latency).  
  - Кастомные метрики: `mes_price_calculation_seconds`, `rabbitmq_messages_processed`.  

- **Настроить RabbitMQ Monitoring**  
  Использовать **RabbitMQ Prometheus Plugin** для сбора:  
  - `rabbitmq_messages` (включая dead letters) с ярлыками `queue`, `vhost`.  
  - `rabbitmq_message_bytes` для объема данных.  

---

### 3. Дашборды и алертинг
- **Создать ключевые дашборды в Grafana**:  
  - **MES**:  
    - Время расчета стоимости (`mes_price_calculation_seconds`).  
    - Загрузка CPU/памяти MES-сервера.  
    - Очереди RabbitMQ, связанные с производством (фильтр по `queue=manufacturing`).  
  - **CRM**:  
    - Количество заказов в статусе `MANUFACTURING_APPROVED` (метрика `orders_by_status`).  
    - HTTP-ошибки API при создании заказов.  
  - **Инфраструктура**:  
    - Использование дискового пространства БД (`node_filesystem_avail_bytes{instance=~"shop_db|mes_db"}`).
